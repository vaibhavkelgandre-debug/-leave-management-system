# 🔐 Role Capability Matrix — Who Can Do What

> **Single source of truth for authorization.** Companion to [`1.functional_requirements.md`](1.functional_requirements.md) and [`2.api_documentation.md`](2.api_documentation.md). Read this before wiring a new route, adding a nav item, or hiding/showing a button by role.
>
> 🚨 **Standing rule:** whenever a role gains, loses, or changes an ability — a new `requireRole(...)` gate, a changed row-level check in a service, a new `RequireRole`/`RoleGate` in the client, a new nav item — **update this document in the same change**. Same standing rule as [`2.api_documentation.md`](2.api_documentation.md) for endpoints and [`3.db.md`](3.db.md) for schema.

## 1. The four roles

| Role | How it's created | Position in the reporting tree | One-line summary |
|---|---|---|---|
| `SUPER_ADMIN` | **Singleton.** `POST /auth/register/hr` with `HR_REGISTRATION_CODE`. 409 if one already exists. | The true root. Can **never** have a manager. Profile is `VERIFIED` at creation. | Acts as HR **only for the `HR_ADMIN`s who report directly to it**. Company-wide read, deliberately narrow write. |
| `HR_ADMIN` | Invited by an existing `HR_ADMIN`/`SUPER_ADMIN` (`POST /users/invite`, `managerId` required). | Reports to another `HR_ADMIN` (whoever created them) or to `SUPER_ADMIN`. Root of its own branch. | Full HR authority **over its own reporting subtree**, plus company-wide read on a few list views. |
| `MANAGER` | Invited by HR (`managerId` optional). | Reports only to an `HR_ADMIN`. | Approves/rejects leave for **direct reports only**; can view their whole subtree; can delegate. |
| `EMPLOYEE` | Invited by HR (`managerId` required). | Reports to a `MANAGER` or an `HR_ADMIN`. | Self-service only — **unless** currently someone's active delegate. |

**Nobody can invite a `SUPER_ADMIN`** — the invite payload only accepts `EMPLOYEE`, `MANAGER`, `HR_ADMIN`.

### Reporting-line rules (enforced on every write that sets `manager_id`)

| Target role | Allowed manager roles |
|---|---|
| `EMPLOYEE` | `MANAGER`, `HR_ADMIN` |
| `MANAGER` | `HR_ADMIN` only (never another manager) |
| `HR_ADMIN` | `HR_ADMIN`, `SUPER_ADMIN` |
| `SUPER_ADMIN` | *none — never gets a manager* |

Reassignment is additionally rejected if it would create a reporting cycle.

## 2. The two questions every check answers

Authorization here is **never role alone**. There are two independent gates:

1. **Role gate** (route level, `requireRole(...)`) — "may this *kind* of user reach this endpoint at all?"
2. **Scope gate** (service level, row level) — "does this user have authority over *this specific person/record*?"

Scopes used throughout this document:

| Scope term | Means | Implemented by |
|---|---|---|
| **Self** | `actor.id === target.id` | inline checks / `/me/*` routes |
| **Direct reports** | one level down only | `findDirectReports` |
| **Subtree** | everyone transitively below, any depth | `isUserInSubtree` / `findSubtreeUsers` |
| **HR scope** | `HR_ADMIN` → own **subtree**. `SUPER_ADMIN` → **direct-report `HR_ADMIN`s only** | [`hrScopeService.js`](../server/src/services/hrScopeService.js) |
| **Creator ownership** | actor must be the target's `invited_by` | `changeManager` / `changeStatus` |
| **Delegate** | an active delegation window covers today | `isManagerOrDelegateOf` |
| **Company-wide** | every user, no scoping | `findAllUsers` / `findAllLeaveRequests` |

> ⚠️ **`SUPER_ADMIN` is not "HR_ADMIN with more power."** Its *read* access is company-wide like HR's, but every HR-scoped *write* reaches **only its direct-report `HR_ADMIN`s** — never those admins' own teams. Reusing subtree scoping for `SUPER_ADMIN` would silently mean "the entire company," which was explicitly rejected.

**Legend for the matrices below:** ✅ allowed · ⚠️ allowed but scoped (condition in the notes) · ❌ denied

## 4. Employee & org-structure management

| Capability | Endpoint | EMPLOYEE | MANAGER | HR_ADMIN | SUPER_ADMIN | Notes |
|---|---|:--:|:--:|:--:|:--:|---|
| Invite a new user | `POST /users/invite` | ❌ | ❌ | ✅ | ✅ | Invitable roles: `EMPLOYEE`, `MANAGER`, `HR_ADMIN`. `managerId` required for `EMPLOYEE` and `HR_ADMIN`, optional for `MANAGER`. |
| List users | `GET /users` | ⚠️ self only | ⚠️ own subtree | ✅ company-wide | ✅ company-wide | No role gate — the **service** decides the slice. |
| View one user | `GET /users/:id` | ⚠️ self only | ⚠️ self + subtree | ✅ company-wide | ✅ company-wide | `requireUserScope`. Sensitive fields masked — see §9. |
| View own team list | `GET /users/me/team` | ⚠️ empty | ✅ subtree | ✅ subtree | ✅ subtree | No role gate; a user with no reports just gets `[]`. |
| Change who someone reports to | `PATCH /users/:id/manager` | ❌ | ❌ | ⚠️ | ⚠️ | HR-tier role gate **plus creator ownership**: the actor must be the target's `invited_by`. Plus hierarchy and cycle checks. |
| Activate / deactivate an account | `PATCH /users/:id/status` | ❌ | ❌ | ⚠️ | ⚠️ | Same creator-ownership rule. You can never deactivate yourself. |
| Open an employee's full detail / verification record | `GET /employees/:id` | ❌ | ❌ | ⚠️ HR scope | ⚠️ HR scope | Deliberately **stricter** than `GET /users/:id` — see §9. |

> 🔒 **Creator ownership is the surprising one.** Any HR admin can *see* every user, but can only re-parent or deactivate accounts **they themselves created**. An account with no `invited_by` (the registered `SUPER_ADMIN`) cannot be re-parented or deactivated by anyone through these endpoints.

## 6. Leave requests

| Capability | Endpoint | EMPLOYEE | MANAGER | HR_ADMIN | SUPER_ADMIN | Notes |
|---|---|:--:|:--:|:--:|:--:|---|
| Preview working days | `POST /leave-requests/preview` | ✅ | ✅ | ✅ | ✅ | Persists nothing. |
| Apply for leave | `POST /leave-requests` | ✅ | ✅ | ✅ | ⚠️ | **`SUPER_ADMIN`'s request is created directly as `APPROVED`** — no reviewer exists. All validation (balance, overlap, document requirement, working days) still applies. |
| Team / approvals queue | `GET /leave-requests/team` | ⚠️ delegated teams only | ⚠️ **direct reports** + delegated teams | ⚠️ HR scope | ⚠️ HR scope | **No role gate** — a plain employee acting as a delegate must reach this. A non-delegate employee gets `[]`, not 403. A manager gets direct reports only, **not** their full subtree. |
| View own requests | `GET /leave-requests/mine` | ✅ | ✅ | ✅ | ✅ | |
| Company-wide "All Requests" (read-only) | `GET /leave-requests/all` | ❌ | ❌ | ✅ | ✅ | Broader than what HR can *act* on — visibility ≠ authority. |
| Filterable browse | `GET /leave-requests` | ❌ | ❌ | ⚠️ HR scope | ⚠️ HR scope | Filtering for someone outside scope returns no rows. |
| Leave-taken report + CSV | `GET /leave-requests/report`, `/report/csv` | ❌ | ❌ | ⚠️ HR scope | ⚠️ HR scope | |
| View one request / its audit trail / its document | `GET /leave-requests/:id`, `/:id/audit`, `/:id/document`, `/:id/document/download` | ⚠️ own | ⚠️ own + as manager/delegate | ✅ company-wide | ✅ company-wide | Denials are **404, never 403** — existence isn't leaked. |
| **Approve / reject** | `POST /leave-requests/:id/approve` `/reject` | ⚠️ only as an active delegate | ⚠️ only as the **assigned** manager, or a delegate for them | ⚠️ only when HR **is** the assigned manager | ⚠️ same | See the box below. |
| Withdraw / cancel | `POST /leave-requests/:id/withdraw` `/cancel` | ⚠️ own only | ⚠️ own only | ⚠️ own only | ⚠️ own only | Owner only; 404 for anyone else regardless of role. |
| **Override a decision** | `POST /leave-requests/:id/override` | ❌ | ❌ | ⚠️ own subtree | ❌ **403** | The one capability `HR_ADMIN` has and `SUPER_ADMIN` does not. |

> ⚖️ **HR has no approval bypass.** The flow is always: *employee submits → the actual assigned manager (or their active delegate) decides → HR may override afterwards.* HR can approve directly **only when HR genuinely is the assigned manager** — which already covers employees with no manager, every `MANAGER` (who only ever reports to an `HR_ADMIN`), and an `HR_ADMIN` reporting to another `HR_ADMIN`.
>
> A blocked HR-tier actor gets **403 with an explanatory message** when the employee is inside their HR scope (they legitimately know the record exists) and **404** when outside it. Nobody — not even HR — can act on **their own** request; that check runs before any role check.

## 9. Field-level and view-level exceptions

The rules that don't fit a simple endpoint row:

1. **Sensitive profile fields are masked.** `pan_number`, `aadhar_number`, `passport_number`, `bank_account_number`, `bank_ifsc_code`, `bank_name` come back in full **only** to the employee themself and to HR-tier viewers. A manager viewing a direct report sees `null` for these. Other fields (phone, address, DOB, emergency contact, designation) are **not** masked — a manager plausibly needs a report's contact details.
2. **`GET /users/:id` is intentionally looser than `GET /employees/:id`.** The first lets any HR admin read any user company-wide (a directory lookup). The second is the verification/detail record and is HR-scope-restricted, matching every other HR *write* action.
3. **Visibility ≠ authority, everywhere.** `GET /leave-requests/all` is company-wide for HR while approving is not; a manager's team list spans their whole subtree while approval authority stops at direct reports.
4. **404 vs 403 is a deliberate choice.** 403 means "you can legitimately see this record, but this particular action isn't yours." 404 means "you have no business knowing this record exists." Preserve the distinction in any new check.
5. **`SUPER_ADMIN` bypasses its own workflows** because nobody sits above it: profile `VERIFIED` at creation, leave requests auto-`APPROVED` with an `AUTO_APPROVE` audit entry and no notification.

## 12. Checklist when you change a role's abilities

1. Change the **route** gate (`requireRole` / `requireUserScope`) *and* the **service** row-level check — the service check is the real one; the route gate is convenience and belt-and-suspenders.
2. Decide **404 vs 403** for the denial and match §9.4.
3. Decide whether `SUPER_ADMIN` follows `HR_ADMIN` here, and whether its scope is direct-reports-only — don't reuse subtree scoping for it by reflex.
4. Update the client guard (`RequireRole` / `RoleGate` / `hasAnyRole`) and the nav entry so the UI never offers something the server will refuse.
5. Add or update tests for **both** the allowed and the denied role.
6. **Update this document** (the matrix row *and* any relevant note in §9), plus [`2.api_documentation.md`](2.api_documentation.md) if the endpoint's contract moved.
